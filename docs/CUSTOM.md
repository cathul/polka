# Polka develop 0.1

Наша версия начинается с **0.1**, независимо от номера оригинального проекта.
База — upstream `vestigiumincaligne/polka`, тег `v0.1.22`, commit
`01c2712a771fc72b7eced5887eea68e6bb1876a0`.

## Что изменено

- Один образ и один контейнер Polka: FB2 → EPUB3 выполняется отдельным
  бинарником `fbc` внутри этого же контейнера. Python-sidecar не нужен.
- Единственные SMTP-настройки находятся в административной панели Polka.
  Каждый пользователь задаёт собственный адрес получателя любого домена.
- В SMTP-разделе администратор включает «Разрешить конвертацию FB2 в EPUB3
  при отправке» и нажимает «Сохранить». По умолчанию конвертация выключена.
  Для FB2 на странице книги появляется выбор «Оригинал (FB2) / EPUB3».
  Обратной конвертации и постоянного кэша нет. Остальные форматы отправляются
  без изменения. Получающий почтовый сервис сам определяет допустимые форматы.
- В OPDS добавлен личный раздел **Want to read** — тот же существующий список
  «Хочу прочитать» веб-интерфейса. Кнопки и смысл списка не переименованы.
  Пользователь скачивает книги по одной; скачивание не удаляет их из списка.
  Плагин KOReader не требуется.
- «Убрать из читаемых» удаляет прогресс только текущего пользователя.
  Действие доступно на странице книги с прогрессом.
  KOReader не блокируется: следующий push может снова добавить книгу.
  Сохранённая позиция на самом устройстве и протокольные данные kosync
  не удаляются. Другие пользователи и списки не затрагиваются.
- Последний успешно использованный серверный путь к INPX сохраняется в базе
  и подставляется в форму. Вручную введённое значение имеет приоритет.
  Выбор файла для загрузки очищает поле серверного пути и наоборот.
  Временные пути загрузок и неудачные импорты не заменяют сохранённый путь.
- Новые настройки, действия, ошибки и описания имеют EN/RU-переводы.
  Название нового OPDS-раздела оставлено английским по согласованному решению.

## Сохранность библиотеки и синхронизация

В upstream веб-импорт с replace удалял `book_digests`, а консольный `--replace`
удалял базу каталога целиком. Числовые ID назначались заново в порядке импорта,
поэтому старые списки и прогресс могли ссылаться на другие книги.

Теперь вне очищаемого каталога хранится `catalog_identities`: соответствие
исторического ID и точного набора `folder + file + ext + size + lib_id`.
При совпадении единственной идентичности ID сохраняется. Новые книги получают
ID выше всех зарезервированных; ID исчезнувшей книги не переиспользуется.
Таким образом, существующие списки, прогресс и рейтинги сохраняют ссылки
на ту же книгу при изменении порядка записей INPX. Если файл позже вернулся
с той же однозначной идентичностью, его прежний ID может восстановиться.

Дайджесты хранят сведения о файле независимо от числового ID. Clear()
транзакционно отсоединяет связи, не удаляя сами дайджесты. После завершённого
импорта они связываются с единственным точным совпадением. Если ID поменялся
в старом каталоге, такая связь может восстановиться на новый ID.
Неоднозначные, отсутствующие и изменившиеся файлы не сопоставляются наугад.
Позднее завершение скачивания использует сведения исходного файла, а не
перечитывает уже переиспользованный ID.

Скачивание из Want to read проходит через обычный обработчик Polka и
регистрирует дайджест. Для синхронизации всё равно нужно настроить kosync
в KOReader и отправить с устройства прогресс. Отправленный по SMTP EPUB
тоже получает связь с исходной книгой. Она применима, если KOReader получит
именно эти байты: обработка Amazon или другого сервиса может изменить файл.
Успех SMTP означает принятие письма сервером, а не доставку на читалку.

### Границы восстановления

- Изменение архивного пути, имени файла, расширения, размера или lib_id
  считается другой идентичностью. Совпадения по названию/автору не угадываются.
- Книга, отсутствующая в каталоге, не показывается в полках и OPDS; её старые
  пользовательские записи сохраняются и не прикрепляются к новой книге.
- Дайджесты, уже удалённые старой версией, автоматически не восстановить.
  Нужны резервная копия либо повторная регистрация неизменённого файла.
- Сведения, которые ещё до перехода на develop уже были связаны со старым
  неверным ID, нельзя достоверно восстановить без исторической копии каталога.
- Совпадение полей каталога не доказывает побайтовое равенство файла:
  незаметная подмена содержимого с теми же полями отдельно не обнаруживается.
- Импорт остаётся пакетным. Ошибка посередине может оставить неполный каталог.
  Сохранённая метка `digest_import_pending=1` запрещает мост KOReader к полкам
  до успешного завершения. Повторить replace или восстановить резервную копию;
  вручную снимать метку нельзя. Неверный ZIP/INPX отклоняется до очистки.
- Удаление прогресса передаётся при desktop/offline sync: старый снимок
  не возвращает удалённую запись. Новое чтение или новый push KOReader снова
  создаёт прогресс; постоянного запрета нет. Для передачи удаления между
  desktop и сервером обе стороны должны использовать эту develop-версию.

Миграции каталога транзакционные. Их версии хранятся в
`meta.custom_digest_identity_version` и `meta.custom_stable_ids_version`,
отдельно от upstream `PRAGMA user_version` (4). Это предотвращает пропуск
будущей upstream-миграции с тем же номером. Более новая неподдерживаемая схема
отклоняется. Возврат к старому образу требует восстановления копии данных.

## FB2: положение в тексте и двусторонняя синхронизация

Серверная веб-читалка умеет сопоставлять нормализованные именованные XPointers
KOReader с исходными текстовыми узлами FB2. В обратную сторону сохраняется
XPointer того слова, которое находится на линии чтения браузера. Координаты
DOM браузера (UTF-16) переводятся в смещения Unicode code points CREngine.
KOReader получает новую позицию обычным запросом kosync; плагин не нужен.

Границы первой реализации:

- Только исходный FB2 с совпадающим KOReader-дайджестом. XPointer от EPUB,
  преобразованной или изменённой копии не применяется к оригинальному FB2.
- Поддерживаются именованные пути с индексами и старые пути без индекса,
  когда элемент/текстовый узел действительно единственный. Начало элемента
  `.0` разрешено только при однозначном первом прямом текстовом узле.
- Не эмулируются ремонт повреждённого XML, таблицы, pre/code, нестандартные
  стили, длинные текстовые чанки CREngine и неоднозначная нормализация пробелов.
  Неизвестные позиции открываются приблизительно и не публикуются обратно
  как точные координаты. Для неточных участков сохраняется обычная веб-позиция.
- Отдельный desktop/offline клиент пока не экспортирует точные координаты
  через state sync: этот мост предназначен для серверной веб-читалки.
- Проверены протокол и сопоставление на фикстурах. Совпадение с реальной
  версией CREngine на устройстве ещё требует проверки; не обещается точность
  для любой разновидности FB2/DOM-версии. Процент разных движков может
  отличаться: переносится место в тексте, а не одинаковая разметка страниц.

Производительность и сохранность:

- Карточка книги, главная и приём обычного kosync не открывают FB2 и не строят
  индекс. Разрешение пути запрашивается веб-читалкой явно (`resolve=1`).
- Первый запуск чтения разбирает текст и читает файл для проверки дайджеста.
  Индекс хранится в существующем ограниченном кэше последних восьми книг.
  Повторные запросы используют кэш; метаданные исходного файла проверяются
  для обнаружения замены архива. Это не фоновая индексация всей библиотеки.
- Запись веб-позиции и записи для KOReader выполняется одной транзакцией.
  Начальная отрисовка, восстановление прокрутки, загрузка шрифтов/картинок
  не сохраняют прогресс до реального действия читателя.
- Не добавлены зависимости, схемы БД или постоянные файлы индексов.

Синтаксис сверен с
[CREngine toStringV2/createXPointerV2](https://github.com/koreader/crengine/blob/master/crengine/src/lvtinydom.cpp)
и [клиентом kosync KOReader](https://github.com/koreader/koreader/blob/master/plugins/kosync.koplugin/main.lua).

## Язык поиска

- В строке поиска интерфейса: один вариант — все языки, русский, украинский
  или английский. Фильтр применяется к названиям, авторам и сериям;
  при переходе из поиска к книгам автора/серии выбор сохраняется в ссылке.
  Обычные страницы авторов/серий без этой ссылки остаются без ограничения.
- Кнопка «Настройки поиска» рядом с именем пользователя открывает личную
  настройку «Язык поиска в OPDS». Она действует исключительно на запросы
  `/opds/search`, независимо от выбора в строке веб-поиска. По умолчанию — все.
- Пустой язык (включая пробелы) всегда включается; регистр кода не важен.
  Используются коды INPX `ru`, `uk`, `en`. При выборе «Все языки» доступны
  любые коды. Подборки, списки и обычная навигация OPDS не фильтруются.
- Схема базы и версия приложения не менялись. Docker-образ после добавления
  языковых фильтров не пересобирался.

## Конвертер и ограничения отправки

Использован тот же источник, что и в старом сервисе:
`https://github.com/rupor-github/fb2cng`, commit
`e526f866d30f19aabfb2134204433e1485d4965d`.

Polka собирается Go 1.26.11; отдельный конвертер требует Go 1.27.1.
В Docker для него используется отдельная стадия сборки, а в финальный Alpine
попадают статический бинарник, сертификаты TLS, лицензия и соответствующий
архив исходников/сгенерированных ресурсов в `/usr/share/licenses/fb2cng/`.
Конвертер сохраняет GPL-3.0, исходная Polka — MIT. Рецепт сборки:
`build/converter-task.yaml` и стадия `converter` в Dockerfile.

Пределы: исходный файл 64 MiB, вложение 18 MiB до MIME/base64, две
одновременные отправки, конвертация до 180 секунд, SMTP-соединение до
30 секунд. При ошибке конвертации исходный FB2 вместо EPUB не отправляется.
Временные файлы удаляются после запроса. Автоматических повторов SMTP нет.

Для самостоятельного запуска вне Docker `fbc` должен быть в PATH либо указан
через `POLKA_FBC_BINARY`. SMTP-логин и пароль через этот параметр не передаются.
В рантайме ничего не скачивается и не устанавливается.

## Разработка и проверки

Рабочая ветка — `develop`; `main` форка остаётся копией upstream.
Удалённые публикации отложены до завершения разработки и локальных проверок.
Не добавлять в Git реальные `.env`, серверные базы, архив `polka.zip` или
папку `polka_old`: они исключены из Git и Docker context. Для сравнений можно
использовать `.local-server/`, предварительно убрав секреты.

Локальные Go и зависимости находятся только в `.tools`, настройки системы
не меняются. Вспомогательный Go 1.27.1 для конвертера также находится там.
Frontend использует зависимости из существующего package-lock.json.

```sh
export GOTOOLCHAIN=local
export GOPATH="$PWD/.tools/gopath"
export GOCACHE="$PWD/.tools/gocache"
.tools/go/bin/go test -tags nodynamic ./...
.tools/go/bin/go vet -tags nodynamic ./...
cd web
npm test
npm run build
cd ..
.tools/go/bin/go build -tags nodynamic -trimpath -ldflags '-X main.version=0.1' -o bin/polka ./cmd/polka
```

Серверные тесты используют временные базы и loopback HTTP/SMTP. Настоящие
письма не отправляются. Для проверки реального конвертера:

```sh
POLKA_TEST_FBC="$PWD/.tools/bin/fbc" .tools/go/bin/go test -tags nodynamic ./internal/converter ./internal/server
```

Масштабные тесты `POLKA_SCALE_BOOKS` не включать без отдельного разрешения.
GitHub CI проверяет develop. Develop Docker workflow ждёт CI и собирает
amd64/arm64. Публикации по push/PR нет; ручной `publish=true` публикует только
в GHCR форка с тегами `develop-0.1-<SHA>` и `develop`. Для сервера выбирать
неизменяемый digest. Старый upstream Release workflow с v-тегами без отдельной
проверки не запускать: он также публикует релизы и latest в GHCR форка.

## Обновления upstream

```sh
git fetch upstream --tags
git switch develop
git status --short
# Сначала сохранить текущие изменения.
git branch backup/develop-before-update
git merge <проверенный-upstream-tag>
```

Особенно внимательно разрешать конфликты схемы, импорта, стабильных ID,
регистрации дайджестов, отправки SMTP, OPDS, frontend и Dockerfile.
Повторить миграционные и интеграционные тесты. Не сбрасывать develop на
upstream/main. Незавершённое слияние можно отменить `git merge --abort`.

## Переход на сервере — выполняет владелец

1. Проверить реальную версию образа, архитектуру и текущий Compose. Сохранить
   идентификатор старого образа и конфигурацию. Рабочий сервер этой разработкой
   не проверялся и не изменялся.
2. Остановить писателей в базы и сделать согласованную резервную копию всего
   data-dir с правами, конфигурации и настроек. Копия только открытого SQLite
   без WAL не является надёжной резервной копией.
3. Сначала проверить новый образ на отдельной копии data-dir, отдельном порту
   и с библиотекой только для чтения. Не подключать одну рабочую базу к двум
   версиям. Проверить обе базы, старые списки/рейтинги/прогресс, импорт,
   OPDS, конвертацию, SMTP и KOReader.
4. В административной панели новой Polka настроить единственный SMTP,
   проверить подключение и включить конвертацию. Для Amazon отправитель должен
   быть разрешён в настройках личных документов аккаунта. Старый `.env`
   sidecar в образ или репозиторий не переносить.
5. В панели Cloudflare удалить отдельное правило отправки в sidecar и
   направить весь домен на IP:порт новой Polka. Проверить и локальный адрес,
   и домен. API использует относительные URL, OPDS — host и схему запроса;
   фиксированный PUBLIC_ORIGIN не требуется. Для OPDS/kosync не должно быть
   интерактивной страницы Cloudflare Access вместо протокольного ответа.
6. После успешных проверок отключить старый sidecar. Изменять серверную
   конфигурацию и Cloudflare будет владелец, не агент разработки.
7. Откат: остановить новую версию, восстановить согласованную копию data-dir,
   старый Compose/образ и прежнее правило Cloudflare, затем вернуть sidecar.
   Не запускать старую версию на изменённой develop-базе.

## Отдельный пример запуска

`docker-compose.develop.yml` — пример пробного развёртывания одного контейнера
на отдельном порту 12792 и отдельном томе `polka-develop-data`. Исходный
`docker-compose.yml` не изменён: он по-прежнему описывает upstream-образ.
Для develop использовать новый файл либо вручную заменить image в своей
согласованной серверной конфигурации после резервного копирования.

В `.env.example` только путь к книгам и адрес/порт привязки. Учётных данных
SMTP там нет: SMTP настраивается только через административную панель.
Пример привязан к loopback для пробного запуска. Если Cloudflare Tunnel
подключается по LAN, владелец должен явно выбрать доступный ему LAN-адрес
привязки при развёртывании. Команды ниже здесь не запускались:

```sh
cp .env.example .env
# Вручную задать свой POLKA_BOOKS_PATH.
docker compose -f docker-compose.develop.yml --env-file .env up -d --build
```
